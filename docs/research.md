# Worktree storage: claim review and decisions

This review checks the attached zero-duplication architecture against primary Git, OS, package-manager and MCP documentation. The attachment is useful as a proposal catalogue; its benchmark figures, universal guarantees and detailed implementation blueprint are not established by those sources. Treat figures such as “0 bytes”, “10–17 MiB”, sub-second creation and exact per-worktree physical usage as hypotheses to measure on target filesystems, not product claims.

## Decisions

1. Start from Git’s ordinary worktree and index semantics. Treat reflinks or overlays as optional filesystem optimizations, not as a Git guarantee.
2. Never expose a mutable checkout through a hardlink farm. If a safe CoW backend is unavailable, use an ordinary checkout/copy fallback.
3. Keep merge computation separate from integration into a checked-out branch. Use Git’s normal merge/update path to keep refs, index and working tree consistent.
4. Share dependency downloads only through package-manager-supported caches. Resolve and install each worktree’s own manifest/lockfile state; do not promise automatic additive lockfile reconciliation.
5. Measure savings as an observed, scoped estimate, not exact per-worktree physical bytes. Keep worktree isolation claims limited to files and resources the implementation actually separates.
6. Implement MCP versions and compatibility according to the versions the chosen SDK supports; do not hard-code an assumed “downgrade” to one old revision.

## Claims and evidence

| Topic | What primary sources support | Decision / correction |
| --- | --- | --- |
| **Git worktrees and source duplication** | Git says linked worktrees share repository data except per-worktree files such as `HEAD` and the index; each still gets its own checkout. Git documents shared refs and per-worktree administrative directories. ([`git worktree`](https://git-scm.com/docs/git-worktree)) | Worktrees avoid duplicating Git object history, but Git does not promise cloned working-tree files, shared build outputs, dependencies, or any disk-space ratio. A separate `git clone` is a different choice and normally has its own object database. |
| **Git subcommand discovery** | Git invokes an executable named `git-<command>` on `PATH` for non-built-in commands. ([`git`](https://git-scm.com/docs/git#_git_commands)) | The proposed `git-graft` executable naming is supported. This says nothing about MCP setup or shared state semantics. |
| **Hardlinks** | A hardlink is another name for the same file/inode, with the same permissions and ownership; writes through either name affect that file. Unlinking removes a name, and storage remains until the last link and open handle are gone. ([`link(2)`](https://man7.org/linux/man-pages/man2/link.2.html), [`unlink(2)`](https://man7.org/linux/man-pages/man2/unlink.2.html)) | Read-only mode is not a CoW barrier: permission changes affect the shared inode, and a writable alias can modify the shared contents. An MCP wrapper cannot intercept arbitrary editor, shell, formatter or build writes. Do not hardlink mutable source trees. Hardlinks are only suitable where the shared object is truly immutable and callers cannot mutate it; package managers’ link layouts are their own contract, not a general guarantee for arbitrary packages. |
| **Immutable overlay lower** | Linux OverlayFS supports shared lower layers, but changes to underlying filesystems while an overlay is mounted are disallowed; behavior is undefined. Upper/work directories cannot be shared between mounts. ([Linux kernel OverlayFS documentation](https://docs.kernel.org/filesystems/overlayfs.html#changes-to-underlying-filesystems), [sharing layers](https://docs.kernel.org/filesystems/overlayfs.html#sharing-and-copying-layers)) | A snapshot pinned to a commit is a reasonable design direction, provided it is actually immutable for the full mount lifetime and each overlay has a valid private upper/work directory. “Snapshotting `main`” from a live dirty checkout, and extracting or cloning files, need explicit index, untracked-file, ignored-file and secret policies. The kernel docs do not promise zero metadata or zero physical allocation. |
| **Reflinks / clone-on-write** | Apple documents APFS clone files as a storage-saving feature; clones share data until writes diverge. ([Apple: About Apple File System](https://developer.apple.com/documentation/foundation/about-apple-file-system)) | Probe the filesystem/API and fall back on unsupported filesystems, cross-volume operations, permission failures or resource limits. CoW is a starting-space optimization, not a fixed cost: modified blocks, metadata, snapshots and compiler outputs consume storage. The attachment’s per-path metadata and timing figures need reproducible local benchmarks. |
| **Symlinks and source isolation** | Git records symlinks as symlinks, and ordinary path traversal follows them; Git’s checkout and index model expects tracked file types to match. ([Git index format](https://git-scm.com/docs/index-format), [POSIX `open`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/open.html)) | Do not substitute tracked regular files with symlink farms. Writes can reach the target, Git sees type changes, and path-resolution behavior varies by tool. Keep a real checkout-shaped tree for source. Symlinked package layouts can be used where the package manager explicitly supports them. |
| **Merge and current checkout** | `git merge-tree --write-tree` computes a merge without reading or writing the working tree or index, and does not create a commit. ([`git merge-tree`](https://git-scm.com/docs/git-merge-tree)) | It is useful for previewing a tree merge; it does not perform an atomic “land and wipe” transaction. Updating a ref alone does not update the checked-out files/index. Integrate via Git in the target worktree, with normal dirty-worktree and race checks; only then clean up the task worktree. A semantic lockfile rewrite is a separate resolver operation, not part of Git’s merge guarantee. |
| **Dependency/build caches** | pnpm describes separate worktree checkouts sharing a content-addressable store and warns this assumes a shared trust boundary. Its layout uses hardlinks for package files and symlinks for dependency structure. ([pnpm worktrees](https://pnpm.io/git-worktrees), [pnpm node_modules layout](https://pnpm.io/symlinked-node-modules-structure)) pnpm documents offline install as “store only” (and failure when an item is absent), distinct from prefer-offline; its frozen-lockfile mode rejects required lockfile updates. ([pnpm install](https://pnpm.io/cli/install)) Cargo stores outputs under `target` by default and documents `sccache` as a way to share build results. ([Cargo build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html)) uv’s cache is reusable, but installation into an environment still depends on filesystem/link mode; it can fall back to copying. ([uv caching](https://docs.astral.sh/uv/concepts/cache/)) | A shared download/content cache can reduce repeated fetching. It does not guarantee each worktree materializes only a tiny dependency delta, avoids build-output divergence, or can regenerate a lockfile offline. Keep mutable install environments and compiler outputs isolated unless a tool explicitly documents safe concurrent sharing. Treat package-manager version, platform, optional/peer dependencies, lifecycle scripts and network availability as resolver inputs. |
| **Disk measurement** | `du` distinguishes apparent file length from filesystem usage; `statfs` reports filesystem-wide block and inode counts. ([GNU `du`](https://www.gnu.org/software/coreutils/manual/html_node/du-invocation.html), [`statfs(2)`](https://man7.org/linux/man-pages/man2/statfs.2.html)) | Free-space deltas describe the whole filesystem, so concurrent processes, snapshots, delayed reclamation, metadata and unrelated writes contaminate attribution. Report method, filesystem, duration and uncertainty. Use controlled before/after experiments and label the result an estimate; do not claim exact per-worktree bytes from a global free-space counter. |
| **Isolation and portability** | Git worktrees share repository data; pnpm explicitly limits its shared-store setup to a common trust boundary. Filesystem primitives have platform/filesystem and mount constraints. ([Git worktrees](https://git-scm.com/docs/git-worktree), [pnpm worktrees](https://pnpm.io/git-worktrees), [OverlayFS requirements](https://docs.kernel.org/filesystems/overlayfs.html)) | A separate working directory isolates edits only to the extent that files are not shared writable aliases. It does not isolate processes, ports, environment variables, credentials, databases, sockets or shared caches. Define those separately. Prefer detected per-volume capabilities with a portable ordinary worktree/copy fallback; do not assert universal rootless overlay or reflink support. |
| **MCP protocol version** | The current specification marks `2026-07-28` and later as per-request version metadata, while `2025-11-25` and earlier use `initialize` negotiation. The server must report unsupported versions and supported versions; standard transports include stdio and Streamable HTTP. ([Versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)) | The attachment’s fixed `2026-07-28` to `2024-11-05` downgrade claim is not a protocol guarantee. Select and test an SDK’s actual version support and compatibility behavior, and implement the corresponding lifecycle/transport. Do not infer client support from the server SDK. |

## Portable implementation path

Ship a conventional Git-backed workspace first. On a detected and tested CoW filesystem, optionally use reflinks; on Linux, consider OverlayFS only when mount prerequisites and immutable-lower rules are met. Otherwise use ordinary checkout/copy semantics. Keep each agent’s source, index, build outputs, mutable environment and runtime state isolated. Share only caches whose owning package manager documents safe sharing, and treat cache hits as an optimization rather than a promise that installs or resolution are offline or delta-only.

Before making storage or speed claims, benchmark representative repositories on each supported OS/filesystem with concurrent builds and writes, record both logical size and the measurement method for allocated space, and include unsupported-backend fallback results. The attached research is a proposal; the cited standards and manuals establish primitive behavior, not this project’s implementation, performance or safety guarantees.
