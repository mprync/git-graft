# Safety and recovery

## Graft contents

The selected commit determines the initial source tree. Local edits in the original checkout stay there, and so do untracked and ignored files unless `add --include`, MCP `include` or the `include` list of the project's `.graftconfig` or `.graftconfig.local` names them. Graft copies those into the new graft without changing the originals. A copy never replaces a file the commit provides, is never written through a symlink in the graft, and holds whatever the original held, including credentials. Eligible files can be verified and shared using copy-on-write, with independently writable file identities. Other files come from Git. Tracked symbolic links retain normal Git semantics and may point outside the graft.

A reused file must be proven before Graft records it: Git's built-in line-ending clean of the primary file, as `git status` compares it and `git add` stores it in the graft, must give exactly the selected commit's blob. Graft models Git's `convert.c` for this, including binary detection under `text=auto` and `core.autocrlf`, the rule that keeps CRLF already in the index, and `core.safecrlf=true` refusals, and its tests compare every decision with Git's own. The proof is either Git's index stat test in the primary, for an unchanged file exactly as large as its blob on a path where Git's clean leaves such a file unchanged, or a hash of the converted bytes against the blob; stat data never stands in for a conversion. Paths with a `filter`, `ident` or `working-tree-encoding` attribute are never reused, because a clean filter can hide edits. Files with flags or user extended attributes are checked out by Git instead. Graft records each installed file's stat data in the new index so the first `git status` reads no file contents. Git builds that compare timestamps in whole seconds cannot see a same-size edit that restores a file's modification time within the same second; Graft's own clean checks, used before merging or removing a graft, compare the nanosecond stamps the index records and hash any such file.

When a merge checks the primary for uncommitted edits, it turns off clean filters defined in the repository's own configuration, so a repository cannot run a command through that check. Filters in your global or system configuration stay on. A lossy clean filter there, one that maps different file contents to the same bytes, can hide a same-size edit from the check, exactly as it hides that edit from `git status` and `git merge`.

A graft owns its Git objects, refs, reflogs, stash and index. It does not automatically receive new refs from the original repository. Merging transfers the selected committed work back. Graft declines unsupported histories and checkout configurations rather than silently changing their meaning.

Ordinary CLI and MCP calls that create a graft and omit the history option honor the primary repository's `graft.history` setting. In an unconfigured project, local history is the default. Existing users who need the previous isolated behavior can set `git config --local graft.history isolated` in the primary repository.

Local history treats the invoking clone’s complete Git object database as trusted input. An agent can enumerate objects from other branches, staged files, deleted branches and dropped stashes if those objects still exist. Only the selected commit supplies the checkout. The snapshot has its own object files and remains readable if the primary runs garbage collection or moves. Where the filesystem cannot clone files, Linux gives the snapshot hard links to the primary's object files instead of clones. Both repositories then name the same immutable files: either can repack, prune or move without affecting the other, but a process that overwrites an object file in place, which Git never does, would change it for both. New commits and edits in one graft stay private until explicitly transferred. Use `--history isolated` when unrelated objects must be excluded and only the selected commit's reachable history should be readable. Use `--history tip` when the graft needs only the starting commit and its files. Git treats that commit as the shallow history boundary. If a local snapshot cannot be made, Graft uses the selected-history path and reports the actual source in `storage.objects.source`.

When reusing a mixed pack, Graft edits an unlinked copy, has Git index its contents, and verifies the object IDs before publishing the pack. On macOS, creating that copy briefly requires an owner-controlled, writable source pack directory. An interruption before unlinking can leave a private temporary directory there, eligible for Git’s normal expiry. The source pack stays intact. If the filesystem or directory cannot support this operation, Graft exports the selected objects through Git.

## Recover work

`merge`, `remove` and `prune` archive the graft: they move its private repository and every file in it, including untracked and ignored files, to `<repo>.graft/.retired/<id>`. Archives therefore keep credentials such as `.env` files, keys and tokens that the graft held. Graft creates graft and archive directories owner-only (mode 0700 on Unix) and keeps each file's own mode; on Windows they inherit the parent's ACLs. Your user account, and any backup of the disk, can still read them. To remove a secret for good, delete it from the graft before archiving it, or from the archive afterwards. Save the returned recovery lease:

| Situation | Action |
| --- | --- |
| Reopen a merged or removed graft | `git graft restore NAME --lease TOKEN`; save the new active lease. |
| Reverse a merge | `git graft merge NAME --undo --lease TOKEN` appends a reversal commit if the destination still points at the merge commit. |
| Destination advanced | Review subsequent commits and use an ordinary reviewed reversal. |
| `destination_has_local_changes` | Your uncommitted edits in the primary touch paths the merge or undo changes, or files there, including ignored ones and any written during the update, lie where it writes. They are listed in `details.paths`. Graft changed nothing; commit those edits or move them aside and retry. Edits to other paths stay as they are through any merge. See [uncommitted edits](operations.md#uncommitted-edits-in-the-primary-checkout). |
| `local_changes` | The graft has uncommitted, untracked or ignored files, listed in `details.paths` with their status. Commit them, or archive the graft with them using `remove --discard` and keep the recovery lease. A shared dependency install that Graft attached and the graft has not changed is not counted. |
| `checkout_recovery_required` | Retry the same merge or undo with the same lease. Graft finishes or reverses the update from the files on disk and keeps untracked, ignored, edited and staged files. If it names `paths`, follow [checkout recovery](operations.md#interrupted-checkout-update). |
| `checkout_update_set_aside` | The branch moved or is no longer checked out after the update stopped. Graft changed no further file, and files the stopped update wrote stay as they are; check `git status` in the primary and retry the merge. |
| `primary_moved` | Every record names one other primary path, so the primary was moved or copied. Graft reads and writes nothing; move the primary back to `details.recorded_primary`. |
| Merge receipt with `"removed": false` | The graft gained commits after the merge applied and stays active. Merge it again to land them. |
| `spawn_incomplete` or a `pending` graft | Retry the same `add` request. Graft archives the unfinished attempt whole, rebuilds the graft and lists the archive in `archived_attempts`; see [interrupted add](operations.md#interrupted-add). |
| `unfinished_creation` | The archive holds a creation that never finished, so restore leaves it exactly as it was. Copy what you need from `details.archive_path`, or run `add` again. |
| Name or path is occupied | Restore fails as `already_exists`. Inspect the collision and preserve the existing data before retrying. |
| `archive_damaged` | The archive at `details.archive_path` is missing or was changed by hand. Restore leaves it exactly as found. Copy what you need from it, or put back the missing Git files and retry. |

When `add` reports a graft, its record, Git objects and branch are on disk and survive a power loss. On macOS the steps before that are ordered with write barriers and flushed once, when the graft is marked active; a power loss earlier leaves part of an unfinished creation, in order, which a retry of the same request archives or replaces. Like `git checkout`, Graft does not flush the files it checks out or clones, or the index it writes. A file cut short by a power loss shows up as modified in `git status`, because its size no longer matches the one the index records, the same as for a file Git checked out.

Archives and recovery records have no automatic expiry and can use disk. Deleting the original repository or Graft's recovery state can prevent recovery. Maintain independent backups for disk failure and accidental deletion.

The first merge prepares its history store privately before publishing it. After an interruption Graft can reclaim first-store scratch whose recorded identity and contents still match. It preserves unrecognized or changed scratch and reports its path on a later merge. Interrupted merge-planning directories can also be left for inspection.

## Trust and cleanup

Graft is not a sandbox. Git hooks, filters, merge drivers, package scripts and explicitly requested commands have the user's operating-system permissions. The MCP host must opt in to execution and dependency tools with `--allow-exec`. A graft's own Git configuration is writable by whoever works in it, so when Graft inspects a graft's status it disables every filter driver defined by repository-scoped configuration; only the user's global and system drivers run. Leases coordinate cooperating clients; they do not protect data from another process running as the same user. Share active and recovery leases only with trusted local tools. Treat leases as sensitive and remove them from logs, issue reports and other shared material. Shell history and process listings may expose command-line arguments. Installed dependency layers must be trusted, relocatable and free of private data.

Turns on a shared resource are cooperative in the same way as leases. Graft records which holder holds the turn and which holders wait for it. It does not start, stop or lock the resource, and it cannot keep a process from using the resource without a turn: any process running as the same user can ignore a turn, or edit the turn state under `.git/graft/turns`. A holder's lease only keeps cooperating clients from using one name by mistake. A turn that is not renewed expires after its ttl, and a holder whose named process has ended or whose named grafts are no longer active is dropped, so an agent that stops without releasing delays the others for no longer than its ttl, or 300 seconds if it was waiting. Turn state holds holder names, digests of their leases, process IDs and start times, graft IDs, names and paths, and times, and never a lease. A shared resource's state is kept in the repository at the configuration's directory, so anyone who can write that repository's Graft state can change its turns. [Take turns on a shared resource](operations.md#take-turns-on-a-shared-resource)

`push` publishes with your credentials. It runs the primary's own `git push`, so a holder of a graft's lease can send that graft's commits wherever the primary's remotes, credential helpers and SSH keys let you push. The reach is limited to one branch per call, on a remote the primary already names, and never forced. A plain `push` does not update the remote's default branch, as `refs/remotes/REMOTE/HEAD` records it, even from a graft whose branch has that name; the caller must name it with `--to`. An MCP host must opt in with `--allow-push`, separately from `--allow-exec`; without it `graft_push` is not listed and a call is refused. A host started with `--allow-exec` can already run any program, `git push` included, so `--allow-push` is the narrower permission for a host that may publish but not execute. Before the push, the commits enter the primary's object store. No branch of the primary points at them; only the private ref Graft removes afterwards and the remote-tracking ref Git writes for the pushed branch do. Everything in the pushed commits becomes readable to whoever can read the remote, so review them first. The primary's `pre-push` hook and the remote's hooks run as for any push, without the lease in their environment. Git's terminal prompt is turned off and SSH runs in batch mode unless you configured an SSH command, but a program named by `GIT_ASKPASS`, `core.askPass` or `SSH_ASKPASS`, or a credential helper's own dialog, can still ask for an answer and hold the push until it gets one. Errors pass on Git's messages with the user and password part of URLs removed; other secrets a remote or hook prints are passed on as they are. [Push to a remote](operations.md#push-to-a-remote)

[Remotes the configuration names](operations.md#remotes-in-a-graft) give a graft URLs that plain `git fetch` and `git push` use, with your credentials, outside `push`: such a push is not limited to one branch, and nothing stops it updating the remote's default branch. Remotes that `.graftconfig`, or a `.graftconfig.local` that needs trust for its hooks, lists are therefore set up only once you have trusted them with `git graft hook trust`, as hooks are; until then `add` and `restore` leave them out of the graft, for an MCP host too. An MCP host started without `--allow-push` gives each such remote a push URL Git refuses, and does the same to a remote a graft it restores already has, so an agent there can fetch but not push through it. An agent that can run commands can still configure a remote of its own, as it can run `git push` from the primary.

Package manager registration stores cache routing and compatibility settings in the project’s private Graft state. Keep credentials out of these settings. Choose a manager cache designed for concurrent access within the project’s trust boundary. Package builds and installers control which files they write. A registered installation can attach only at an unoccupied checkout-relative path with matching committed inputs. [Manager registration](operations.md#register-a-package-manager)

A [hook](operations.md#hooks) is a command from the project's [configuration](operations.md#configure-a-project). Graft runs it with the user's permissions and environment, in the graft, whenever a graft is added, about to be archived or restored. A hook in a committed `.graftconfig` is part of the repository, so Graft runs the hooks in `.graftconfig`, and in `.graftconfig.local` once Git tracks it, only after you trust them with `git graft hook trust`, and runs them again after a change only once you trust the change. Until then every command that would run one of them refuses with `hooks_untrusted` and runs nothing: cloning a repository, or checking out a contributor's branch, and running `git graft add` runs none of its hooks. Read the hooks with `git graft hook list` before you trust them, as you would read a repository's build scripts. Trust covers each hook's event, name and arguments, and not the contents of the program it starts, except a program named relative to a directory above the checkout: a hook such as `node scripts/setup.js` runs whatever that script holds when the hook runs, so trust a hook only when you also trust what its program and arguments name. Keep personal hooks and patterns in `.graftconfig.local`, and add that file to `.gitignore` so it is never committed; while Git does not track it, its hooks need no trust, except on Windows when the file is in a directory above the checkout.

Graft reads both files from the primary checkout's working tree, or, when its root holds neither, from the nearest directory above it that holds either, never from a graft. For a checkout inside your home directory, the search stops at home, so a stray or broken file in a directory that holds homes, such as `/Users`, or at the root of the filesystem, does not configure or break your repositories; a checkout outside home is searched up to the root. On Unix, a file above the checkout that belongs to another user, or that sits in a directory or behind a link that does, is refused, so a file planted in a shared directory such as `/tmp` cannot run commands as you. Windows does not check who owns such a file, so there every hook from a file above the checkout runs only once trusted, including one from a `.graftconfig.local` that Git does not track: anyone who can write to a parent directory, such as a shared folder or the root of a drive, can place one. A hook there may name its program by a path relative to that directory, outside the repository and every directory of grafts, after following links and, on macOS and Windows, ignoring case; trust then also covers that program's contents. A graft's uncommitted edits to its own copy of `.graftconfig`, and commits it has not merged, do not change what runs. A commit that changes a hook in `.graftconfig` reaches the primary when it is merged into the primary's checked-out branch, and from then on every command that would run hooks refuses with `hooks_untrusted` until you have read the change with `git graft hook list` and trusted it. An agent without `--allow-exec` that edits `.graftconfig` in its graft and merges it therefore cannot have its hook run by your next `add`. An agent that can write the primary's files, or run the CLI, can define or trust a hook, as it can already run any command. There is no MCP tool that defines or trusts a hook, and an MCP host runs configured hooks only when it was started with `--allow-exec`; otherwise it reports them as skipped and runs nothing, which also means a graft can be archived over MCP without its `pre-archive` cleanup. A hook never receives a lease. Name hook programs by absolute paths that agents cannot write to: a program inside a graft lets the graft's files decide what a later `merge` or `remove` runs. The configuration refuses a relative path with a directory in it for the same reason. A bare name is looked up in `PATH`, so it is only as safe as every directory in `PATH`. Graft does not undo what a hook did when the command then stops for another reason.

After a power loss, a registered install cache can contain incomplete files. Graft verifies the saved generation before reuse and preserves a damaged one for inspection. The graft can run a fresh package restore. A cache purge interrupted after quarantine also retains its quarantine directory and reports it on the next preview.

Use `git graft prune` to preview cleanup before applying it with `git graft prune --apply`. Close editors and builds that can write into a graft before moving or removing it. If other native Git checkouts share the primary, finish any checkout creation or branch switch before merging. Git tracks their branch occupancy separately from the destination ref lock.

On macOS, Graft rejects extended allow ACL entries on its primary private registry and managed graft root, including entries inherited before publication. It does not change permission entries, and it does not walk ordinary source ACLs outside these gates.

On Windows, Graft relies on inherited ACLs and does not verify private DACLs. Use a private Git administrative directory and a graft parent whose ACLs allow only trusted users; apply the same care to custom graft destinations.

### Commands running at once

Grafts build in parallel. An `add` holds the project's registry lock only while it reserves its name and while it records the finished graft, and the first build to need a missing shared cache fills it while the others wait to reuse it. `merge`, `push`, `remove`, `prune --apply`, `restore`, `move`, `repair`, `exec`, dependency and cache commands wait until the builds in progress finish, so none of them changes the primary, a parent graft or a shared cache under a build. A [hook](operations.md#hooks) runs with the registry lock and the build lock released, under its own graft's lock, so a slow hook delays only commands on that graft. `list`, `status`, lease renewal, `lock`, `unlock` and the `turn` commands do not wait for builds, though they do wait while one of those commands is queued behind a build; `list` shows a graft still being built with the phase `creating`. Retrying an `add` while its first attempt is still building waits for it and replies with the same graft.

### Processes left running in a graft

`exec` shares the graft's lock with the process it starts, and that process passes the lock on to the processes it starts in turn. While any of them still holds it, `merge`, `push`, `remove`, `prune`, `move`, `lock` and dependency changes report `workspace_busy`, even after `exec` has returned. A job left running in the background, such as `nohup npm run dev &`, keeps the graft busy until it exits; further `exec` calls, lease renewals and `turn` commands still work. Stop the job before you merge or archive the graft.

On Windows, a new process receives every inheritable handle of the process that starts it, so a background job also receives `exec`'s output pipes and keeps them open even when it writes nothing. `exec` therefore returns two seconds after the process it started exits, with the output captured so far; anything written to those pipes later is not captured. Graft keeps its own standard input and output out of that inheritance, so the program that called Graft gets its result without waiting for the job. The job still holds the graft only if the process that started it passed its handles on, as Node.js, Rust and most programs that start other programs do; a process started without inherited handles, such as one opened through the Windows shell, is not seen.

Graft cannot see a process that closes inherited files, such as a daemon, a child that Python's `subprocess` starts with its default `close_fds=True`, or a child that Node.js starts on macOS. It also cannot see processes it did not start, such as an editor or a terminal. If one of these is still writing when the graft is archived, it keeps writing into the archive under `.retired`, because the archive is the same directory renamed. Nothing is lost, but a later `restore` shows those writes. On Windows, an open file or a working directory inside the graft usually makes the archive rename fail, and the operation can be retried after the process exits.
